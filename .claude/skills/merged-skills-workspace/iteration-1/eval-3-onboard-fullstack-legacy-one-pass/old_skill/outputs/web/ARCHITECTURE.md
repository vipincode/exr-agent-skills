## Stack

- **Vite 6** + **`@vitejs/plugin-react` 4** — a client-side SPA. **No Next.js, no App Router,
  no Pages Router, no Server Components, no server layer of any kind.**
- **React 18.3** — everything is a client component; `"use client"` is meaningless here and must
  not be added.
- **react-router-dom 6.28** — client-side routing, declared as `<Routes>/<Route>` elements in
  `src/App.tsx`, wrapped in `<BrowserRouter>` in `src/main.tsx`.
- **MUI 6** (`@mui/material`) + **Emotion 11** (`@emotion/react`, `@emotion/styled`) — the
  component library and the styling engine. **No Tailwind, no shadcn/ui, no CSS Modules, no
  Sass.** Styling is MUI props (`variant`, `mb={2}`) and the MUI theme.
- **SWR 2.2** — server-state / data fetching. **Not TanStack Query.**
- **axios 1.7** — one configured instance in `src/api/client.ts`.
- **Formik 2.4** + **Yup 1.4** — forms and validation. **Not React Hook Form, not Zod.**
- **State management: none.** No Redux/Zustand/Jotai, and no React Context except MUI's
  `ThemeProvider`. Server state lives in SWR; local state in `useState`.
- **TypeScript 5.6**, `strict: true`, `jsx: "react-jsx"`, `module: ESNext`,
  `moduleResolution: "bundler"`, `"type": "module"`.
- **Test:** jest 29 + `@testing-library/react` 16 (devDependencies). **No test files, no jest
  config, no setup file, and no jsdom/transform configured yet.**
- **Package manager:** npm assumed (no lockfile committed in the scanned tree).
- **Lint:** `eslint .` is in `scripts`, but **no ESLint config file exists** and no `eslint`
  dependency is installed — the script would fail as-is.

## Project layout — type-grouped (not feature-modules)

Files are grouped **by kind**, not by feature. There is no `src/features/` folder and no
`components/ui` + `components/shared` split.

```
src/
  main.tsx            entry — createRoot, ThemeProvider, BrowserRouter, <App />
  App.tsx             the route table (<Routes>/<Route>)
  api/                client.ts — the axios instance + the SWR fetcher
  components/         generic shared components (Card, PageHeader)
    forms/            form components (LoginForm)
  hooks/              data hooks (useUsers) — SWR wrappers
  pages/              route screens, default-exported (UsersPage, LoginPage)
  schemas/            Yup validation schemas (userSchema.ts)
  theme/              theme.ts — the MUI createTheme object
```

**New work follows this shape**: a screen goes in `src/pages/` (default export, PascalCase file),
its route is registered in `src/App.tsx`, its data hook goes in `src/hooks/`, its request layer
goes through `src/api/client.ts`, its Yup schema goes in `src/schemas/`, and its components go in
`src/components/` (generic) or `src/components/forms/` (form UI). **Do not create
`src/features/<name>/`** — it would conflict with the entire existing tree.

There is **no `index.html`, no `public/`, and no root `index.css` in the scanned tree** — the
Vite entry HTML is expected at the project root; `main.tsx` mounts into `#root`.

## Import convention — relative paths, no alias

`tsconfig.json` sets `baseUrl: "."` but **no `compilerOptions.paths`**, and `vite.config.ts`
defines **no `resolve.alias`**. Every import is relative:
`import { fetcher } from "../api/client";`, `import { loginSchema } from "../../schemas/userSchema";`.
**There is no `@/` alias — do not emit one**; it will not resolve.

## Component placement

Two tiers only, both hand-rolled on MUI:

- **`src/components/`** — generic, domain-agnostic reusables composed from MUI primitives
  (`Card` wraps MUI `Card`/`CardContent`/`Typography`; `PageHeader` wraps `Box`/`Typography`).
  Named exports, PascalCase filenames.
- **`src/components/forms/`** — form components (`LoginForm`). Also named exports.
- **MUI itself is the primitive layer.** Need a button/input/dialog? Import it from
  `@mui/material` — **never** hand-write a primitive and never `shadcn add` anything.

Before creating any component/hook/schema/util: **check `MODULE_REGISTRY.md` first**, then grep
`src/components`, `src/hooks`, `src/schemas`, `src/api`. If a suitable piece exists, import it.

## Forms — Formik + Yup

- A form is `useFormik({ initialValues, validationSchema, onSubmit })` — the **hook** form, not
  the `<Formik>` render-prop component or `<Form>/<Field>` components.
- Fields are **MUI `TextField`s wired by hand**: `name`, `value={formik.values.x}`,
  `onChange={formik.handleChange}`, `error={!!formik.errors.x}`, `helperText={formik.errors.x}`.
  **There is no shared `*Field` component layer** — new forms repeat this wiring, matching
  `LoginForm`. (Introducing a shared field layer is a Finding, not a rule.)
- Validation schemas are **Yup**, in `src/schemas/`. Types are **not** derived from schemas —
  interfaces are hand-written where needed (see `User` in `src/hooks/useUsers.ts`).
- Submission calls the axios instance directly inside `onSubmit`
  (`await apiClient.post("/auth/login", values)`) — there is no mutation-hook layer.

## Data fetching — SWR + one axios instance

- **`src/api/client.ts`** exports:
  - `apiClient` — `axios.create({ baseURL: import.meta.env.VITE_API_URL })`. **The one HTTP
    instance; always reuse it.** No interceptors, no auth header, no error normalization.
  - `fetcher(url)` — `apiClient.get(url).then(r => r.data)`, the SWR fetcher.
- **Data hooks live in `src/hooks/`** and wrap `useSWR<T>(key, fetcher)`, returning renamed
  fields (`useUsers` returns `{ users, error, isLoading }`). **Query keys are plain URL strings**
  (`"/users"`) — not arrays, not namespaced.
- **Mutations have no hook layer** — components call `apiClient.post(...)` inline.
- Consumers render `if (isLoading) return <p>Loading…</p>` and then the data. There is no error
  UI, no `<ErrorBoundary>`, and no global SWR config (`SWRConfig` is not mounted).

## Backend connection — DIRECT to the API (no BFF)

The browser calls the backend's **absolute URL** — `baseURL: import.meta.env.VITE_API_URL`
(`web/.env.example` → `VITE_API_URL=https://api.example.com`). This is a pure SPA with **no
server**, so a BFF/proxy is not merely missing — there is nowhere to host one. Vite's
`server.proxy` is also not configured.

**This is the recorded reality.** Do not introduce `app/api/` Route Handlers or a same-origin
`/api` baseURL. The backend (`api/`) enables this with `cors({ origin: CORS_ORIGIN })`.

> Path note: the API mounts products at **`/api/products`**, so full paths through this client
> are `${VITE_API_URL}/api/products`. The existing hooks call `/users` and `/auth/login`, which
> the backend does **not** serve — see Findings.

## Auth & routing

- **Routes** are declared in `src/App.tsx`: `/` → `UsersPage`, `/login` → `LoginPage`.
- **There is no route protection.** No guard component, no HOC, no redirect, no role→route map.
  `/` renders the users screen for anyone.
- **There is no session layer.** `LoginForm` posts to `/auth/login` and **discards the
  response** — no token is stored (no cookie, no `localStorage`), no axios request interceptor
  attaches an `Authorization` header, and nothing redirects after login. The backend's
  `requireAuth` expects `Authorization: Bearer <token>`, so **no authenticated request this
  client makes can currently succeed.** An auth feature must add token storage + an axios
  interceptor + a guard; nothing exists to reuse yet.

## Theming

`src/theme/theme.ts` exports `theme = createTheme({ palette: { primary: { main: "#1976d2" } } })`
(MUI's default blue, stated explicitly). It is applied once in `src/main.tsx` via
`<ThemeProvider theme={theme}>`. Only `palette.primary` is customized — no typography, spacing,
shape, or component-override entries, no dark mode, and no `CssBaseline`.

Design tokens are MUI theme values, consumed through MUI props / `sx`. **There is no
`globals.css`, no oklch token set, and no Tailwind theme** — the `font-theme-setup` skill (which
targets Tailwind v4 + shadcn) does **not** apply to this project.

## Environment

Raw **`import.meta.env`** (Vite), read in exactly one place today (`src/api/client.ts`). There is
no typed env module (no T3 Env, no config wrapper) and no runtime validation — a missing
`VITE_API_URL` silently yields a relative baseURL.

Vite's rule applies: **only `VITE_`-prefixed vars reach the browser**, and everything in an SPA
is public — never put a secret here. Declared in `web/.env.example`:

| Var | Read in | Purpose |
| --- | --- | --- |
| `VITE_API_URL` | `src/api/client.ts` | absolute base URL of the `api/` backend |

New vars are added to `.env.example` and read via `import.meta.env` at the use site.

## Feature workflow

Work is planned **per module** and built **one slice at a time**:

1. Build the screens first from a design source — `figma-to-component` (Figma),
   `html-to-component` (HTML/URL), or `project-to-component` (another codebase). **Caveat:
   those builders emit Next.js + Tailwind + shadcn; this project is Vite + MUI + Emotion, so
   their output must be translated to this contract before it lands here.**
2. `module-planner` writes `_docs/features/<module>/<module>-plan.md` plus ordered slice files
   (`01-<slice>.md`, …) — the number is the build order. These live under `_docs/features/` at
   the **repo root**, not in this project folder, because a plan spans backend and frontend and
   each slice states the API contract once for both halves.
3. You review and edit those files.
4. `module-builder` executes **one slice**: it writes the binding layer (an SWR hook in
   `src/hooks/` + calls through `src/api/client.ts`) and edits the already-built screens to
   consume it, then marks the slice `built`.
5. `test-writer` covers it; `code-review` checks it against this contract. Both on demand.

Only this file (`ARCHITECTURE.md`) and `MODULE_REGISTRY.md` live at this project's root — `web/`,
recorded in `.claude/workspace.json` at the repo root, which is how the skills locate it.

## Findings — observed issues (recorded, NOT fixed)

Onboarding is non-destructive; nothing below was changed.

1. **The client calls endpoints the backend does not serve.** `useUsers` fetches `/users` and
   `LoginForm` posts `/auth/login`; `api/` only exposes `GET /health`, `GET /api/products`,
   `GET /api/products/:id`, and `POST /api/products`. Also note the `/api` prefix is missing
   from these paths. The users screen cannot load and login cannot work against this backend.
2. **Login is a dead end.** The `POST /auth/login` response is discarded — no token stored, no
   redirect, no auth header on subsequent requests. Combined with the backend's `requireAuth`,
   every protected call would 401.
3. **No route protection at all** — `/` is public, and there is no role→route mapping despite
   the backend's `user`/`admin` roles and `requireAdmin` gate.
4. **No BFF** — expected for a Vite SPA (there is no server), but it means `VITE_API_URL` and
   every token the app ever holds live in browser-visible JS. Noted without alarm.
5. **Response-shape mismatch.** The backend wraps everything in `{ data, message }`, but
   `fetcher` returns `r.data` (the whole axios body = `{ data, message }`) while `useUsers` types
   it as `User[]`. Consumers would need `result.data`; the type is currently a lie. `strict: true`
   does not catch this because the generic is asserted, not inferred.
6. **No shared form-field layer.** `LoginForm` wires MUI `TextField`s by hand; the **password
   field has no `error`/`helperText`**, so its validation message never renders. Repeating this
   pattern will repeat the bug.
7. **No error UI anywhere.** `useUsers` returns `error` and `UsersPage` ignores it; there is no
   error boundary and no toast/snackbar layer.
8. **No mutation layer.** Components call `apiClient.post` inline, so no loading/error state,
   no cache invalidation, and no revalidation after writes.
9. **`lint` script is broken** — `eslint .` with no ESLint config and no `eslint` dependency.
10. **Tests are unrunnable as configured** — jest with no transform/jsdom against ESM + TSX.
11. **No typed env** — raw `import.meta.env` with no validation; a missing `VITE_API_URL` fails
    silently at runtime.
12. **No `SWRConfig`** — no shared revalidation/error-retry policy or global error handler.
13. **Duplication check: clean.** Exactly one HTTP client, one data-fetching library, one form
    library, one component library, one theme. No duplicate Button/Card/date helpers were found.
