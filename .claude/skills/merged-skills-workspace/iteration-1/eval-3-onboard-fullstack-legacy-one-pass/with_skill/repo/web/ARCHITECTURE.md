> **This file is DESCRIPTIVE.** It was generated by `project-onboard` from a read-only scan

## Stack

- **Vite 6 + React 18 SPA** — no Next.js, no server layer, no Server Components, no
  `"use client"` directive. Every component is a client component; `"use client"` must
  **not** be added.
- **react-router-dom 6** for client-side routing. `<BrowserRouter>` wraps `<App />` in
  `src/main.tsx`; routes are declared as `<Routes>/<Route>` in `src/App.tsx`.
- **TypeScript 5.6**, `strict: true`, `module: ESNext`, `moduleResolution: bundler`,
  `jsx: react-jsx`. ESM (`"type": "module"`).
- **MUI 6** (`@mui/material`) + **Emotion** (`@emotion/react`, `@emotion/styled`) —
  the component library **and** the styling system. There is **no Tailwind, no shadcn/ui,
  no CSS Modules, no global stylesheet.**
- **SWR 2** for server state (reads). **No TanStack Query, no Redux, no Zustand.**
- **axios 1.7** — one configured instance in `src/api/client.ts`.
- **Formik 2 + Yup 1** for forms and validation. **No React Hook Form, no Zod.**
- **Test:** jest 29 + `@testing-library/react` 16 declared in `devDependencies` and
  `npm test` → `jest`, but there are **no test files and no jest config** in the repo yet.
- **Package manager:** no lockfile is committed; assume **npm** until a lockfile says
  otherwise.

Nothing above should be swapped for the toolkit's greenfield equivalent as a side effect of
feature work. Adding a second library alongside one of these (e.g. TanStack Query next to
SWR, Zod next to Yup) is a duplication bug.

## Project layout — type-grouped, not feature-module

```
web/
  src/
    main.tsx            entry: createRoot → <ThemeProvider><BrowserRouter><App/>
    App.tsx             the route table (<Routes>/<Route>)
    pages/              one file per route, PascalCase, DEFAULT export (UsersPage.tsx, LoginPage.tsx)
    components/         shared/generic components, PascalCase, NAMED export (Card.tsx, PageHeader.tsx)
      forms/            form components (LoginForm.tsx)
    hooks/              data + behavior hooks, camelCase `use*.ts` (useUsers.ts)
    schemas/            Yup schemas (userSchema.ts)
    api/                the axios instance + SWR fetcher (client.ts)
    theme/              the MUI theme (theme.ts)
  vite.config.ts        @vitejs/plugin-react only
  tsconfig.json
  .env.example
```

There are **no `src/features/`, `src/lib/`, `src/services/`, `src/types/`, or
`src/constants/` folders**, and no feature-module anatomy. New code follows the existing
type-grouped shape: a new screen is `pages/<Name>Page.tsx` plus a `<Route>` entry in
`App.tsx`; its data hook goes in `hooks/`, its schema in `schemas/`, its form in
`components/forms/`.

If a domain grows large enough to warrant grouping, prefer a subfolder inside the existing
kind folders (`components/products/`, `hooks/products/`) over introducing a parallel
`features/` tree — one layout, consistently.

## Import convention

Relative imports with **no extension** and **no path alias**. `tsconfig.json` sets
`baseUrl: "."` but declares **no `paths`**, so `@/...` does not resolve — do not use it.
Imports look like `import { Card } from "../components/Card";`.

## Component placement

- **`src/components/`** — generic, domain-agnostic reusables (`Card`, `PageHeader`).
  Flat files at the root of `components/`, except forms.
- **`src/components/forms/`** — Formik form components.
- **Pages compose; they do not define reusable UI.** A page (`pages/*.tsx`) wires hooks to
  components and nothing else — see `UsersPage.tsx`.
- **MUI is the primitive layer.** Never hand-roll a button/input/dialog; import it from
  `@mui/material` or compose an existing wrapper. `Card` and `PageHeader` are the
  established pattern: a thin, typed wrapper around MUI primitives.

Before creating any component/hook/schema/util: **check `MODULE_REGISTRY.md` first**, then
grep `src/components`, `src/hooks`, `src/schemas`, `src/api`. If a suitable piece exists,
import it — never recreate.

## Styling & theme

- Styling is **MUI's system**: component props (`variant`, `mb`, `sx`) and the theme.
  Emotion is present as MUI's engine; `styled()` is available but not currently used.
- **`src/theme/theme.ts`** is the single `createTheme(...)` call (today: `palette.primary.main
  = "#1976d2"`), provided by `<ThemeProvider>` in `main.tsx`. Colors, spacing, and typography
  changes go **there**, not into per-component hex values.
- There is no `globals.css`, no CSS reset (`<CssBaseline/>` is **not** mounted), and no
  design-token file.

## Data fetching — SWR for reads, the axios instance for writes

- **Reads:** `useSWR<T>(key, fetcher)` inside a `use*` hook in `src/hooks/`, which returns a
  named-shape object rather than the raw SWR result — `useUsers()` returns
  `{ users, error, isLoading }`. New data hooks follow that shape.
- The SWR **key is the request path** (`"/users"`), and the shared `fetcher`
  (`src/api/client.ts`) resolves it through the axios instance and returns `r.data`.
- There is **no global `SWRConfig` provider** and no cache/revalidation configuration —
  SWR defaults apply.
- **Writes/mutations:** called directly through `apiClient` (e.g.
  `apiClient.post("/auth/login", values)` inside `LoginForm`'s `onSubmit`). There is no
  mutation-hook layer and no `useSWRMutation`.
- **All HTTP goes through the `apiClient` axios instance** — never a bare `fetch`, never a
  second axios instance.

## Backend connection — direct to the API (no BFF)

- The browser calls the backend's **absolute URL**: `apiClient` is created with
  `baseURL: import.meta.env.VITE_API_URL` (`src/api/client.ts`).
- This is a pure SPA — there is no server to host a BFF, so "no BFF" is expected here, not
  a defect. It does mean the backend URL is public and any token lives in the browser.
- **Note a real mismatch:** the backend mounts its routes under `/api/...`
  (`/api/products`), but `VITE_API_URL` in `.env.example` is `https://api.example.com`
  with no `/api` suffix, and the app calls `"/users"` and `"/auth/login"` — neither of
  which the backend implements. Confirm the base URL and the endpoint paths before binding
  new screens; see the onboarding findings.

## Forms & validation — Formik + Yup

- A form is a component in `src/components/forms/` using `useFormik({ initialValues,
  validationSchema, onSubmit })` and a plain `<form onSubmit={formik.handleSubmit}>`.
- Fields are **MUI `<TextField>` wired by hand**: `name` / `value={formik.values.x}` /
  `onChange={formik.handleChange}` / `error={!!formik.errors.x}` /
  `helperText={formik.errors.x}`. There is **no shared `*Field` component layer** —
  see the findings; adding one is a recommendation, not the current convention.
- Validation schemas are **Yup**, in `src/schemas/`, named `<thing>Schema` and exported as
  named exports. Reuse the existing schema before writing a new one.
- `onSubmit` is `async` and calls `apiClient` directly.

## State management

**Server state only.** SWR holds fetched data; there is no Redux/Zustand/Jotai store and no
React Context beyond MUI's `ThemeProvider`. Local UI state is component `useState`. Do not
introduce a global store for a single screen's needs.

## Environment

- **Raw `import.meta.env`**, Vite-style. Browser-exposed vars **must** be prefixed
  `VITE_`. There is no typed env module (no T3 Env, no config file) and no validation.
- Today there is exactly one read, and it is centralized: `VITE_API_URL` in
  `src/api/client.ts`. **Keep it that way** — read env in `src/api/client.ts` (or a future
  `src/config.ts`), not scattered through components.
- `.env.example` is the declared list (`VITE_API_URL`). Add new vars there in the same
  change. Local values go in `.env.local`.

## Auth & routing

- Routes are declared in `src/App.tsx`: `/` → `UsersPage`, `/login` → `LoginPage`.
- **There is no auth implementation.** `LoginForm` posts to `/auth/login` and **discards
  the response** — no token is stored, no axios request interceptor attaches an
  `Authorization` header, there is no session/user context, no `useAuth`, no logout, and
  **no route protection of any kind** (no guard component, no redirect, no role map).
- The backend expects `Authorization: Bearer <token>`. Whoever builds auth must add the
  token storage + an axios interceptor in `src/api/client.ts` (one place), plus a route
  guard, rather than attaching headers per call site.

## Naming

- Page files: `PascalCase` ending in `Page` (`UsersPage.tsx`), **default** export.
- Component files: `PascalCase` matching the component (`Card.tsx`, `PageHeader.tsx`),
  **named** export.
- Hooks: `use<Thing>.ts` exporting `use<Thing>` (`useUsers.ts`), named export.
- Schemas: `<domain>Schema.ts` exporting `<thing>Schema` (`userSchema.ts` → `loginSchema`).
- Domain interfaces are declared **next to the hook that returns them** (`User` is exported
  from `hooks/useUsers.ts`) — there is no `types/` folder yet.

## Feature workflow

Work is planned **per module** and built **one slice at a time**:

1. Build the screens first from a design source — `figma-to-component` (Figma),
   `html-to-component` (HTML/URL), or `project-to-component` (another codebase). They render
   sample data; nothing is bound yet. **Those skills must target MUI + the theme in
   `src/theme/theme.ts`, not Tailwind/shadcn.**
2. `module-planner` writes `_docs/features/<module>/<module>-plan.md` plus ordered slice
   files (`01-<slice>.md`, `02-<slice>.md`, …) — the number is the build order. These live
   under `_docs/features/` at the **repo root**, not in this project folder, because a plan
   spans backend and frontend and each slice states the API contract once for both halves.
3. You review and edit those files.
4. `module-builder` executes **one slice**: it writes the binding layer (a `use*` SWR hook
   and/or an `apiClient` call) and edits the already-built screens to consume it, then marks
   the slice `built`.
5. `test-writer` covers it from that slice's testing checklist; `code-review` checks it
   against this contract. Both on demand.

Only this file (`ARCHITECTURE.md`) and `MODULE_REGISTRY.md` live at this project's root —
`web/`, recorded in `.claude/workspace.json` at the repo root, which is how the skills
locate it.
