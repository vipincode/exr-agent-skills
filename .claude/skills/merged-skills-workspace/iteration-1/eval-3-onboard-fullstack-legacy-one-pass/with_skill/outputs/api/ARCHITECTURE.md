## Stack

- **Express 4** (`express@^4.18.2`) — Express 4 does **not** forward async rejections
  to the error middleware. Every async route handler **must** be wrapped in
  `catchAsync` (`src/utils/catchAsync.ts`). This wrapper is required, not optional.
- **TypeScript 5.1**, **CommonJS** (`module: commonjs`, `moduleResolution: node`),
  `strict: false`. Target ES2020.
- **Mongoose 7** for data (`mongoose@^7.4.0`).
- **jsonwebtoken 9** for token signing/verification (HS256 by default, secret from
  `process.env.JWT_SECRET`). **Not JOSE.**
- **bcryptjs 2** is installed as a dependency but is **not yet used anywhere** — it is
  the intended password-hashing library for the auth feature when it is built.
- **Joi 17** for request-body validation, via `middleware/validate.ts`. **Not Zod.**
- **morgan** (`morgan("dev")`) for HTTP request logging, **cors** for CORS.
  No helmet, no compression, no rate limiting, no pino/winston.
- **Test:** jest 29 + supertest 6 declared in `devDependencies` and `npm test` → `jest`,
  but there are **no test files and no jest config** in the repo yet.
- **Package manager:** no lockfile is committed; assume **npm** until a lockfile says
  otherwise.

## Paradigm — layered (type-grouped), not domain-module

Files are grouped by **role**, not by domain. A single resource is spread across
sibling folders:

```
src/routes/<name>.routes.ts      → Router, mounts middleware + controller fns
src/controllers/<name>.controller.ts → catchAsync-wrapped request/response handling
src/services/<name>.service.ts   → business logic + data access, throws ApiError
src/models/<name>.ts             → Mongoose model (PascalCase file name)
```

`products` (`routes/product.routes.ts` + `controllers/product.controller.ts` +
`services/product.service.ts` + `models/Product.ts`) is the canonical example of this
paradigm. **New modules imitate it** — do not introduce `src/modules/<name>/` folders.

## Import convention

Relative imports with **no file extension** (`import { catchAsync } from "../utils/catchAsync";`).
This is CommonJS + `moduleResolution: node` — do **not** add `.js` extensions.

There are **no TypeScript path aliases** (`compilerOptions.paths` is unset). All
intra-project imports are relative.

## Project layout

```
api/
  src/
    index.ts          app creation + middleware + route mounting + mongoose.connect + listen
                      (single file — there is no separate app.ts/server.ts split)
    controllers/      <name>.controller.ts — named exports, each wrapped in catchAsync
    services/         <name>.service.ts — named exports, plain async functions
    routes/           <name>.routes.ts — default-exports an express Router
    models/           PascalCase Mongoose models (Product.ts, User.ts)
    middleware/       auth.ts, errorHandler.ts, validate.ts  (singular "middleware")
    utils/            ApiError.ts, catchAsync.ts, formatDate.ts
  tsconfig.json       rootDir src → outDir dist
  .env.example
```

Anything reused by two or more modules belongs in `src/utils/` (helpers, error types) or
`src/middleware/` (request-pipeline concerns) and **must** be listed in
`MODULE_REGISTRY.md`. There is no `src/lib/`, `src/config/`, `src/types/`, or
`src/constants/` folder today; if one becomes necessary, prefer extending `utils/` first
so the layout stays consistent.

Cross-module needs go through the other module's **service** (`services/*.service.ts`),
never its model.

## Response envelope (one shape — `{ data, message }`)

Every endpoint, success and error, returns the same two keys. There is **no `success`
flag** and no `meta` key.

```jsonc
// success — controllers, verbatim
{ "data": <payload>, "message": "OK" }
// error — rendered only by middleware/errorHandler.ts
{ "data": null, "message": "<error message>" }
```

There are **no `ok()` / `created()` envelope helpers**. Controllers build the envelope
inline with `res.status(<code>).json({ data, message })`. New controllers do the same —
`message` is the literal string `"OK"` on success unless there is a reason to say more.

List endpoints put pagination *inside* `data`, e.g.
`{ data: { items, total, page, limit }, message: "OK" }` (see
`services/product.service.ts#listProducts`).

## Error model

- **`ApiError`** (`utils/ApiError.ts`) — a single class, `new ApiError(status, message)`.
  There are **no subclasses** (`NotFoundError`, `ConflictError`, … do not exist) and no
  machine-readable `code` field.
- Two factory helpers exist and should be reused: `notFound(what)` → 404
  `"<what> not found"`, and `conflict(msg)` → 409.
- Services `throw` `ApiError` / the factories. Controllers do **not** try/catch — they are
  wrapped in `catchAsync`, which forwards the rejection to `next`.
- **`middleware/errorHandler.ts`** is the single place the error envelope is rendered.
  It maps `err instanceof ApiError ? err.status : 500` and emits
  `{ data: null, message: err.message || "Server error" }`.
- **Mongoose and Joi errors are NOT normalized.** There is no `db-errors` layer, so a
  `CastError`, a duplicate-key `11000`, or a Mongoose `ValidationError` currently falls
  through as a generic 500 with the driver's raw message. New code should either validate
  up front (Joi) or throw an explicit `ApiError`; do not assume normalization exists.
- Error messages and stacks are **not** suppressed in production today.

## Validation flow

- **Joi 17**, applied as route middleware: `validateBody(schema)` from
  `middleware/validate.ts`. It validates `req.body` with `{ abortEarly: false }`, throws
  `new ApiError(422, error.message)` on failure, and assigns the coerced value back onto
  `req.body`.
- Only the **body** is validated — there is no params/query validation helper. If one is
  needed, extend `middleware/validate.ts` rather than writing a second middleware.
- **There are no schema files in the repo yet** and `validateBody` is currently unused.
  New modules should add a Joi schema (e.g. `src/schemas/<name>.schema.ts` or alongside
  the routes file) and mount `validateBody(schema)` on write routes.
- Types are hand-written TypeScript, **not** derived from schemas (Joi has no `z.infer`
  equivalent in use here).

## Auth primitives

- **`middleware/auth.ts`** ships two guards, both already wired into
  `routes/product.routes.ts`:
  - `requireAuth` — reads the `Authorization: Bearer <token>` header, `jwt.verify`s it
    with `process.env.JWT_SECRET`, and assigns the payload to `(req as any).user`.
    Throws `ApiError(401)` when the token is missing or invalid.
  - `requireAdmin` — checks `(req as any).user?.role !== "admin"` → `ApiError(403)`.
    Must be mounted **after** `requireAuth`.
- Transport is a **Bearer token in the Authorization header** — not cookies.
- `req.user` is reached via `(req as any).user`; there is **no** `types/express.d.ts`
  module augmentation. Follow the existing cast, or add the augmentation as a deliberate
  change.
- **There are no sign/issue helpers.** Nothing in the repo calls `jwt.sign` yet, and the
  `User` model (`models/User.ts`, with `email` / `passwordHash` / `name` /
  `role: "user"|"admin"`) has **no routes, controller, or service**. Login / register /
  refresh are a feature for `module-planner` + `module-builder` to design; they should
  add a token helper next to the guards and hash with the already-installed `bcryptjs`
  rather than introducing a new crypto or token library.

## Environment config

- **Raw `process.env`, read at the point of use.** There is no `config/env.ts`, no Zod or
  envalid validation, and no startup failure on missing vars. Reads live in
  `src/index.ts` (`CORS_ORIGIN`, `MONGO_URL`, `PORT`) and `middleware/auth.ts`
  (`JWT_SECRET`).
- No `dotenv` and no `--env-file` flag — the process expects env vars to already be in the
  environment.
- `.env.example` is the declared list: `PORT`, `MONGO_URL`, `JWT_SECRET`, `CORS_ORIGIN`.
  **New vars must be added to `.env.example` in the same change.**

## Logging

`morgan("dev")` on the request pipeline; everything else is `console.*` (`src/index.ts`
logs `"api up"` on listen). There is no logger module, no request id, and no `req.log`.
New code follows the same convention — do not introduce pino/winston without an explicit
decision.

## Build & scripts

- `npm run dev` — `nodemon --exec ts-node src/index.ts`
- `npm run build` — `tsc -p .` (emits to `dist/`; `dist/` is **not** cleaned first)
- `npm start` — `node dist/index.js`
- `npm test` — `jest` (no config or test files present yet)

There are **no** git hooks (no husky/lint-staged), no ESLint config, and no `clean` script.

## Tests

jest + supertest are installed but nothing is configured or written. When tests are added,
`test-writer` should establish the convention (jest + `ts-jest`/babel + supertest for
route-level integration) rather than assume one exists. Assertions must target the
`{ data, message }` envelope described above.

## Naming

- Route/controller/service files: `<name>.<role>.ts`, lowercase singular
  (`product.routes.ts`, `product.controller.ts`, `product.service.ts`).
- Model files: **PascalCase singular** (`Product.ts`, `User.ts`), exporting a PascalCase
  model constant.
- Utils/middleware files: camelCase (`catchAsync.ts`, `formatDate.ts`, `errorHandler.ts`,
  `validate.ts`) — except `ApiError.ts`, which is PascalCase after the class it exports.
- `routes.ts` files default-export their `Router`; controllers, services, utils, and
  middleware use **named exports**.
- Routes are mounted under `/api/<plural>` in `src/index.ts` (`/api/products`).
  `/health` is mounted at the root, outside `/api`.

## Feature workflow

Work is planned **per module** and built **one slice at a time**:

1. `module-planner` writes `_docs/features/<module>/<module>-plan.md` plus ordered slice
   files (`01-<slice>.md`, `02-<slice>.md`, …) — the number is the build order. These live
   under `_docs/features/` at the **repo root**, not in this project folder, because a plan
   spans backend and frontend.
2. You review and edit those files.
3. `module-builder` executes **one slice**, then marks it `built`.
4. `test-writer` covers it from that slice's testing checklist; `code-review` checks it
   against this contract. Both on demand.

Only this file (`ARCHITECTURE.md`) and `MODULE_REGISTRY.md` live at this project's root —
`api/`, recorded in `.claude/workspace.json` at the repo root, which is how the skills
locate this project.

## Decisions log

- Layout: **layered / type-grouped** (`controllers/`, `services/`, `routes/`, `models/`,
  `middleware/`, `utils/`) — not domain-module.
- **Express 4 + `catchAsync` wrappers are mandatory** on every async handler.
- Envelope: **`{ data, message }`**, built inline; no `success` flag, no envelope helpers.
- Errors: single `ApiError(status, message)` + `notFound`/`conflict` factories; one
  renderer in `middleware/errorHandler.ts`; no DB/validation error normalization.
- Validation: **Joi** via `validateBody` (body only).
- Auth: **jsonwebtoken**, Bearer header, `requireAuth`/`requireAdmin` guards; no token
  issuing yet; `bcryptjs` installed for the future auth feature.
- Env: **raw `process.env`**, declared in `.env.example`, unvalidated.
- Logging: **morgan + `console`**.
- CommonJS, extensionless relative imports, no path aliases, `strict: false`.
- Onboarded by `project-onboard` — contract is descriptive; the divergences from the
  toolkit's greenfield defaults are listed as findings in the onboarding report, not
  applied here.
