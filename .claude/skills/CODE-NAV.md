# Code Navigation Protocol

> The companion to [`LAYOUT.md`](./LAYOUT.md). LAYOUT.md answers *which folder* a skill works in;
> this file answers *how a skill finds code inside it without burning tokens*. Every skill that
> reads code follows it.

## Why this exists

Searching is cheap; **opening files to understand them is what costs tokens.** As an app grows,
"open files until you find the helper" goes from a few thousand tokens to tens of thousands per
task. The fix is the same one a senior developer uses: know the map, then read only the file you
are about to change.

## The ladder — cheapest first, stop as soon as you have the answer

| Rung | Source | Answers | Cost |
|---|---|---|---|
| 1 | `<proj>/codemap/INDEX.md` → one shard | *What exists and where?* Every exported function/type/schema/constant with file, signature, one-line purpose; module public surfaces and mount paths. | ~1–3k tokens |
| 2 | `<proj>/MODULE_REGISTRY.md` | *What is it for / what was decided?* Curated purposes, module ownership, decisions log. | ~1–3k tokens |
| 3 | GitNexus MCP tools — **only if connected** | *How is it connected?* Who calls this, what breaks if it changes, which flows a diff touches. | one tool call, capped with `maxTokens` |
| 4 | Grep | *Confirm* a name or catch something the map missed (non-exported code, string literals). | ~hundreds of tokens |
| 5 | Read the file | Only the files you will change, or whose exact behaviour you must match. | the real cost — minimize |

Rules:

- **Map before grep, grep before read.** Never open a file just to learn whether something exists — the code map answers that.
- **The map is generated, so trust it for existence** — but it only lists *exported* symbols. Module-private helpers aren't in it; they don't need to be, because nothing outside the module may use them.
- **Read a file before editing it**, always. The map is a table of contents, not the code.
- If the map looks stale (a listed symbol is missing from its file), run `<pm> run codemap` and continue. In a bootstrapped project it is regenerated on every commit, and `codemap:check` fails CI when stale.
- No `codemap/` folder (an onboarded or non-bootstrapped project)? Skip rung 1; the registry plus grep is the fallback. Recommend adding the generator (`scripts/codemap.ts` from express-ts-bootstrap) as a finding — don't add it silently.

## Rung 1 — the code map (bootstrapped backends)

```
<proj>/codemap/
  INDEX.md               shard table + every module's public surface and mount path
  lib.md  middleware.md  config.md  types-constants.md  app.md  test-helpers.md
  modules/<name>.md      every exported symbol in that module, file by file
```

Typical reads:

- *"Is there already a pagination / id / date helper?"* → INDEX.md → `lib.md`.
- *"What can I call on the user module?"* → INDEX.md's module surfaces (the `index.ts` exports — the only legal imports).
- *"What's in the module I'm about to extend?"* → `modules/<name>.md`, then open only the files the slice changes.
- *"Which test helpers exist?"* → `test-helpers.md`.

Generated by `scripts/codemap.ts` (TypeScript parser, syntax-only, deterministic). Descriptions come from comments: a comment followed by a blank line describes the **file**; a comment directly above an export describes **that symbol** — so write a one-line `/** … */` above every export worth finding.

## Rung 3 — GitNexus (optional)

[GitNexus](https://github.com/abhigyanpatwari/GitNexus) indexes the repo into a code knowledge graph
(functions, classes, imports, call chains) and exposes it over MCP. It answers relationship
questions the map can't. **It is optional**: every skill must work without it, and no skill installs
or configures it — the user opts in.

**Detect:** GitNexus is available only if `mcp__gitnexus__*` tools are present in this session. If
not, skip this rung silently (mention it at most once, in a hand-off, as an option).

**When it earns a call:**

| Situation | Tool | Use the answer to |
|---|---|---|
| About to change anything exported from a module's `index.ts` or from `lib/`/`middleware/` | `impact` | List every caller that must keep working; widen verification to them. |
| Need a symbol's callers, callees, and usages | `context` | Decide reuse vs extend without opening every caller. |
| Reviewing or finishing a change | `detect_changes` | Find flows/modules the diff affects beyond the edited files. |
| Concept search where names are unknown ("where do we send emails?") | `query` | Get candidate symbols, then confirm in the map/file. |
| Which handler serves an endpoint / which frontend calls it | `route_map`, `api_impact` | Contract work across backend and frontend. |

- Always pass `maxTokens` (start ~2000) — unbounded graph answers defeat the purpose.
- Treat results as **leads**, then confirm in the code map or file before acting. An index can be
  stale; if a result names something that no longer exists, fall back to rungs 1/4 and tell the user
  to re-index.
- Never use GitNexus write tools (`rename`) unless the user explicitly asked for that operation.

**Setup (the user runs this — never a skill):**

Requirements: Node `^22.18` or `>=24.11`. License: **PolyForm Noncommercial 1.0.0** — commercial use
needs a commercial license from the authors; say so before recommending it for a company project.

```bash
# a persistent install is more reliable than npx (npx re-extracts the package on each run)
npm i -g gitnexus

# from the repo root — --index-only writes ONLY the .gitnexus/ index (no injected files)
gitnexus analyze --index-only

# connect Claude Code to its MCP server
claude mcp add gitnexus -- gitnexus mcp
# without a global install:  claude mcp add gitnexus -- npx -y gitnexus@latest mcp
#                  Windows:  claude mcp add gitnexus -- cmd /c npx -y gitnexus@latest mcp
```

- Use `--index-only`. A plain `gitnexus analyze` also installs its own skills into `.claude/skills/`,
  registers Claude Code hooks, and writes `AGENTS.md` / `CLAUDE.md` sections — that collides with this
  toolkit's skills and the generated, strict-subset `CLAUDE.md`. If it was run without the flag,
  `gitnexus uninstall` previews removal (`--force` applies it).
- Re-index after changes: re-run the same command (incremental), or `--watch` while working.
- `.gitnexus/` is a local index — keep it gitignored. `analyze` also records the repo in a global
  registry under `~/.gitnexus` (outside the repo); `gitnexus remove <name>` / `gitnexus clean` undo it.
- **Windows:** the first `analyze` right after installing can abort with *"Analyzer … changed while its
  identity was being computed"*. GitNexus fingerprints its own files and a background scanner touching
  freshly installed files trips that check. Wait a minute and re-run — it succeeds once the files
  have been scanned.

**Verified** (GitNexus 1.6.12, Node 24.15, Windows, 2026-10-10) on a bootstrapped backend: indexing
took ~33 s (393 nodes, 766 edges); `--index-only` created only `.gitnexus/`; NodeNext `.js` imports
resolved correctly; `impact`, `context`, and `detect_changes` returned correct callers/flows at
~400–750 tokens per call, and `maxTokens` was honored over MCP.
