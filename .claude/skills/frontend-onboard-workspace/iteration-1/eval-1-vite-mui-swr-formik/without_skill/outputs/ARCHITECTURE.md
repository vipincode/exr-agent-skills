# Frontend Architecture

Descriptive contract file for this codebase. Generated by onboarding the existing repo — it documents the conventions actually in use, not a target/ideal stack. Other frontend-toolkit skills (feature planner, module builder, test writer, code review) should read this before touching the project so new work matches what's already here.

## 1. Stack Summary

| Concern | Choice | Evidence |
|---|---|---|
| Build tool | Vite 6 | `vite.config.ts`, `package.json` scripts (`vite`, `vite build`, `vite preview`) |
| Framework | React 18 (client-rendered SPA, not Next.js) | `react`, `react-dom` in `package.json`; `src/main.tsx` uses `ReactDOM.createRoot` |
| Language | TypeScript, strict mode | `tsconfig.json` (`"strict": true`) |
| Routing | `react-router-dom` v6, client-side `<Routes>/<Route>` | `src/App.tsx`, `src/main.tsx` (`BrowserRouter`) |
| UI library | MUI (`@mui/material`) + Emotion | `src/theme/theme.ts`, component imports from `@mui/material` |
| Data fetching | `swr` hooks + a shared `axios` instance | `src/hooks/useUsers.ts`, `src/api/client.ts` |
| HTTP client | `axios`, single instance in `src/api/client.ts` | — |
| Forms | `formik` | `src/components/forms/LoginForm.tsx` |
| Validation | `yup` (NOT zod) | `src/schemas/userSchema.ts` |
| Styling | MUI theme + `sx`/component props (no Tailwind, no CSS modules seen) | `src/theme/theme.ts` |
| Testing | `jest` + `@testing-library/react` (configured in `package.json`, no test files present yet) | `package.json` devDependencies |
| Env vars | Vite-style `import.meta.env.VITE_*`, documented in `.env.example` | `src/api/client.ts`, `.env.example` |

This stack is deliberately different from the Next.js + shadcn/ui + Zod + TanStack Query + React Hook Form template some of the frontend skills default to. Any skill operating on this repo must follow the table above, not the default template.

## 2. Data-Fetching Pattern (important — no BFF layer)

- There is **no Next.js-style BFF/proxy route**. The browser calls the backend directly.
- `src/api/client.ts` creates one shared `axios` instance with `baseURL` from `VITE_API_URL`, plus a `fetcher(url)` helper that unwraps `.data`.
- Data hooks wrap `useSWR` around that `fetcher`, e.g. `src/hooks/useUsers.ts`:
  ```ts
  const { data, error, isLoading } = useSWR<User[]>("/users", fetcher);
  ```
- Types for API responses are currently declared inline next to the hook that uses them (see `User` in `useUsers.ts`), not in a dedicated `types.ts`. There is no shared `types/` directory yet.
- Mutations (e.g. login) call `apiClient.post(...)` directly inside a Formik `onSubmit`, not through a SWR mutation helper.
- New data-fetching code should follow this same shape: one `useX` hook per resource in `src/hooks/`, backed by `useSWR` + the shared `apiClient`/`fetcher`.

## 3. Forms & Validation

- Forms use `formik`'s `useFormik` hook directly in the component (no shared form wrapper/factory yet).
- Validation schemas are `yup` objects, kept in `src/schemas/` (e.g. `userSchema.ts` exports `loginSchema`).
- Form fields are wired manually to MUI `TextField` via `formik.values` / `formik.handleChange` / `formik.errors` (no Formik `<Field>`/`<ErrorMessage>` abstraction in use).
- Convention: one schema file per domain in `src/schemas/<domain>Schema.ts`; forms live in `src/components/forms/<Name>Form.tsx`.

## 4. Theming & Shared UI

- Single MUI theme object in `src/theme/theme.ts`, applied via `<ThemeProvider>` at the root in `src/main.tsx`.
- Generic, reusable presentational components live directly in `src/components/` (flat, not under a `shared/` subfolder) — e.g. `Card.tsx`, `PageHeader.tsx`.
- Domain/feature-specific components (forms tied to a schema/endpoint) live in `src/components/forms/`.
- There is no `components/ui/` (no shadcn) and no separate `features/<name>/` module tree — this is a much flatter structure than the Next.js template.

## 5. Routing & Pages

- Routes are declared centrally in `src/App.tsx` using `react-router-dom`'s `<Routes>/<Route>`.
- Page-level components live in `src/pages/` (`LoginPage.tsx`, `UsersPage.tsx`) and compose components from `src/components/` plus data hooks from `src/hooks/`.
- No nested/layout routes or route-based code splitting present yet.

## 6. Project Structure

```
src/
  api/
    client.ts        # shared axios instance + swr fetcher (direct-to-backend, no BFF)
  components/
    Card.tsx          # generic shared presentational component
    PageHeader.tsx     # generic shared presentational component
    forms/
      LoginForm.tsx    # feature form (formik + yup + apiClient)
  hooks/
    useUsers.ts        # SWR data hook, resource-per-hook convention
  pages/
    LoginPage.tsx
    UsersPage.tsx
  schemas/
    userSchema.ts       # yup validation schemas
  theme/
    theme.ts             # MUI theme
  App.tsx                # route table
  main.tsx                # app entry: ThemeProvider + BrowserRouter + App
```

Naming: PascalCase component files (`Card.tsx`), camelCase hook/util files with a `use`-prefix for hooks (`useUsers.ts`), camelCase schema files suffixed `Schema.ts`.

## 7. Environment Variables

- Vite convention: only variables prefixed `VITE_` are exposed to client code, read via `import.meta.env.VITE_*`.
- Documented in `.env.example` at repo root. Currently: `VITE_API_URL`.
- No server-side/secret env vars in this app (it's a pure SPA hitting an external API directly).

## 8. Testing

- `jest` + `@testing-library/react` are configured as devDependencies and `npm test` runs `jest`, but no test files exist in the repo yet and no Jest config file (e.g. `jest.config.*`) was found — a test writer skill should check for/establish one (likely via `ts-jest` or `babel-jest` given the TS + Vite setup) before assuming a working setup.

## 9. Known Gaps / Notes for Future Feature Work

- No shared `types/` directory — API response types are inline per hook. Consider a per-resource `types.ts` (mirroring `schemas/`) as the app grows, but do not introduce this speculatively; follow whatever the next feature actually needs and keep it consistent with existing `useUsers.ts` if left inline.
- No BFF/proxy layer — all requests go straight from the browser to `VITE_API_URL`. Do not introduce Next.js-style API routes; this is a Vite SPA.
- No shared form wrapper — each form re-implements the Formik wiring by hand. Do not force a shared abstraction unless asked; match `LoginForm.tsx`'s style for new forms.
- No barrel (`index.ts`) files under `components/`, `hooks/`, `schemas/`, or `pages/` — imports are direct file paths throughout.
