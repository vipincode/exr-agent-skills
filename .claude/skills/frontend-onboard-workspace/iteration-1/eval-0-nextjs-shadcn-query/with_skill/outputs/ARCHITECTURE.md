## Project layout

```
src/
  app/                     routes (App Router). Server Components unless marked "use client".
    api/[...path]/route.ts BFF Route Handler — the ONLY thing that talks to the backend directly.
    providers.tsx           QueryClientProvider, client component.
    layout.tsx               wraps children in <Providers>.
    page.tsx                  renders the products feature's ProductList.
  components/
    ui/                      shadcn primitives (CLI-managed). Installed: button, input.
    shared/                  generic, domain-agnostic reusables built ON ui/. Present subfolders:
      form/                  RHF *Field components. Only InputField so far.
      typography/            Only Heading so far (no Text/Label yet).
      (no overlay/, layout/, or data-display/ subfolders exist yet)
  features/<name>/           self-contained module. products/ has:
    types.ts                 domain types (manual interface, not derived from schema.ts)
    schema.ts                 Zod schema(s) for this module
    hooks/                     TanStack Query hooks
    api/                        request fns hitting the BFF for this module
    components/                 components that depend ONLY on this module
    index.ts                     barrel for the module's public surface
    (no constants/ or template/ subfolders present in the products feature yet)
  hooks/                    cross-feature hooks — use-auth.ts (placeholder, see Auth below).
  lib/                      axios, query-client, env, utils(cn) — cross-cutting singletons/utils.
                             (no lib/auth/ subfolder exists yet)
```

A feature folder owns its files and should never cross-import another feature; anything used by
2+ features belongs in `components/shared`, `lib`, or `hooks`, and **must be listed in
`MODULE_REGISTRY.md`**.

## Component placement (the rule this repo already follows)

- **`components/ui/`** — shadcn primitives, CLI-managed (`button.tsx`, `input.tsx`). Add more via
  the shadcn CLI; never hand-duplicate.
- **`components/shared/`** — generic/domain-agnostic reusables composing `ui/`, grouped by
  purpose (`form/`, `typography/` exist today). `Heading` (typography) and `InputField` (form)
  are the two examples in the repo. Follow this grouping for any new shared piece
  (`overlay/`, `layout/`, `data-display/` are not yet in use — create them the first time a
  matching component is needed, don't invent an alternate location).
- **`features/<name>/components/`** — components that depend on a single feature's domain
  (`ProductCard`, `ProductList` in `features/products/components/`). Move to `components/shared`
  only when a second feature needs them, and register in `MODULE_REGISTRY.md` when moved.

Before creating any component/util/hook/type: check `MODULE_REGISTRY.md` first, then grep
`components/shared`, `lib`, `hooks`. If a suitable piece exists, import it — never recreate.

## Forms — React Hook Form + Zod, via shared fields

- `InputField` (`components/shared/form/input-field.tsx`) is the one shared field that exists; it
  binds RHF via `useController` and wraps `ui/input`. Follow this pattern for any new field type
  (e.g. `SelectField`, `TextareaField`) — add it to `components/shared/form/` and register it,
  don't wire a bare `useController`/`<Controller>` in feature/page code.
- No form in the repo yet uses `useForm({ resolver: zodResolver(...) })` end-to-end — `schema.ts`
  (Zod) and `InputField` (RHF) exist independently. When wiring the first real form, follow the
  toolkit's standard shape (`useForm` + `zodResolver` + shared `*Field`s), and flag the
  resolver/zod version pairing (see Findings).
- Schemas are Zod (`features/<name>/schema.ts`); prefer deriving types via `z.infer` where a
  schema exists. `features/products/types.ts` currently defines `Product` by hand rather than
  from `productSchema` — new features should derive from the schema where practical, but don't
  silently "fix" the existing `products` feature as a side effect of onboarding.

## Typography — cva primitives, compose don't duplicate

- `Heading` lives in `components/shared/typography/heading.tsx`, `cva`-based
  (`level: h1/h2/h3`). No `Text` or `Label` component exists yet — add them to the same folder
  when needed, following `Heading`'s `cva` pattern.
- `Button` (`components/ui/button.tsx`) already carries its own `cva` variants
  (`variant`, `size`) — extend/compose it, never re-skin or re-implement.

## Data fetching — TanStack Query through the BFF

- Server-state via TanStack Query v5. The client is constructed once in
  `lib/query-client.ts` and provided in `app/providers.tsx`.
- Hooks (`useProducts`) live in `features/<name>/hooks/`, call fns from
  `features/<name>/api/`, and use array query keys namespaced by feature (`["products"]`).
- All requests go through the `axios` instance (`lib/axios.ts`) → same-origin `/api` → the BFF
  Route Handler → the backend. No component/hook calls `fetch`/the backend URL directly.

## Backend connection — BFF proxy (never direct)

- The browser only ever calls same-origin `/api/...`. `src/app/api/[...path]/route.ts` forwards
  every method (`GET/POST/PUT/DELETE`) to `${env.BACKEND_URL}/<path>`, using the incoming
  request's headers/body/method.
- This keeps the backend URL and any tokens out of browser JS. New API integrations should add
  routes/consumers through this same proxy pattern, not call the backend directly from the client.

## Auth & routing

- **Current state is a placeholder, not a real implementation.** `src/hooks/use-auth.ts` is a
  client hook holding local `useState<{id, role} | null>` initialized to `null` — it does not
  read a session, cookie, or token anywhere.
- There is **no** `lib/auth/` folder (no `session.ts`, `roles.ts`, or `tokens.ts`), **no**
  `middleware.ts`/`proxy.ts` for route protection, and **no** login route under `app/api/auth/`.
  Treat auth/session/route-protection as **not yet built** in this repo — the first real auth
  work here should establish the session/token strategy and route-protection layer explicitly
  (a normal `frontend-feature-planner` + `frontend-module-builder` task), not assume one exists.
- Role → route mapping: none defined yet.
