# ARCHITECTURE.md

Descriptive source of truth for this frontend's actual conventions, generated by scanning the existing codebase. This is **not** aspirational — every pattern below is observed in real files (paths cited). Planning/build/test/review work on this repo should follow what's documented here so new code matches what's already there.

## Stack

- **Framework**: Next.js 15 (App Router), React 19, TypeScript (strict mode, `tsconfig.json`)
- **Styling**: Tailwind CSS v4 + shadcn/ui, style `new-york` (`components.json`)
- **Data fetching**: axios (single configured instance) + TanStack Query v5 (server state)
- **Validation**: Zod v4 — used both for env validation and feature schemas
- **Forms**: React Hook Form + `@hookform/resolvers`
- **Env validation**: `@t3-oss/env-nextjs`
- **Class merging**: `class-variance-authority` (variants) + `clsx` + `tailwind-merge` via a shared `cn()` helper
- **Test runner**: Vitest + `@testing-library/react` (configured in `package.json`; no test files exist yet)

Package manager / lockfile were not present in the repo at scan time — none of the commands above have been run, only static files were inspected.

## Path aliases

`tsconfig.json` / `components.json`:
- `@/*` → `src/*`
- `@/components` → `src/components`
- `@/components/ui` → `src/components/ui`

Always import via `@/...`, never relative paths that cross feature/shared boundaries.

## Folder structure

```
src/
  app/                      # Next.js App Router
    api/[...path]/route.ts  # BFF catch-all proxy (see below)
    layout.tsx              # Root layout, wraps children in <Providers>
    page.tsx                 # Route entry, composes feature components
    providers.tsx            # Client-side provider tree ("use client")
  components/
    ui/                      # shadcn primitives (Button, Input, ...) — generated/low-level, not domain-aware
    shared/<category>/       # Hand-built reusable pieces, grouped by category (form/, typography/, ...)
  features/<feature>/        # One folder per domain feature
    api/<feature>.api.ts     # axios calls, envelope unwrapping
    components/              # Feature-specific components
    hooks/                    # Feature-specific hooks (TanStack Query wrappers)
    schema.ts                # Zod schema(s) + inferred input types
    types.ts                 # Domain types (e.g. entity shape returned by API)
    index.ts                 # Barrel export — the ONLY import surface other code should use
  hooks/                     # Cross-feature/global hooks (e.g. use-auth.ts)
  lib/                       # Framework-agnostic infra: axios instance, query client, env, cn()
```

## BFF proxy pattern

`src/app/api/[...path]/route.ts` is a catch-all route that forwards every method to `${env.BACKEND_URL}/${path}`. The **browser never calls the backend directly** — it only ever calls same-origin `/api/*`. `src/lib/axios.ts` enforces this with `baseURL: "/api"` and `withCredentials: true`.

Any new feature's API calls must go through this same axios instance (`@/lib/axios`), never a new axios instance or a raw `fetch` to an external host.

## Env validation

`src/lib/env.ts` uses `@t3-oss/env-nextjs`. `BACKEND_URL` is server-only (used by the BFF route, not exposed to the client). New env vars should be added to this file's `server`/`client` blocks, validated with Zod, not read via raw `process.env`.

## Feature module convention

Observed end-to-end in `src/features/products/`:

1. `types.ts` — plain TS interface for the domain entity (`Product`).
2. `schema.ts` — Zod schema + `z.infer` input type, used for form/mutation input validation (not for parsing GET responses in the current code — see gap below).
3. `api/<feature>.api.ts` — one function per endpoint, calls `api.get/post/...` via the shared axios instance, unwraps the response envelope (`{ data: T }`) before returning.
4. `hooks/use-<feature>.ts` — thin TanStack Query wrapper (`useQuery`/`useMutation`) around the api function, `queryKey` is a plain string array (e.g. `["products"]`).
5. `components/` — presentational components that consume the hook; list/detail components are marked `"use client"` when they use hooks.
6. `index.ts` — barrel file re-exporting only the public surface (top component, hooks, types). Other code (e.g. `app/page.tsx`) imports the feature exclusively through this barrel, never by reaching into `features/<name>/components/...` directly.

**Gap observed**: `fetchProducts` in `src/features/products/api/products.api.ts` types the response but does not `productSchema.parse()` it — response validation with Zod is declared as a schema but not yet wired into the fetch path. Note this when building new features; decide consistently whether the API layer should validate responses, don't silently diverge per feature.

## Component placement rules (inferred)

- `src/components/ui/` — generic shadcn-style primitives, no domain knowledge, styled with `cva` + `cn()` (see `button.tsx`, `input.tsx`).
- `src/components/shared/<category>/` — reusable but hand-authored pieces that compose `ui/` primitives and add behavior (e.g. `shared/form/input-field.tsx` wraps `ui/input.tsx` with RHF's `useController`). Grouped by category subfolder (`form/`, `typography/`), each category has its own barrel `index.ts` where present.
- `src/features/<feature>/components/` — anything specific to one domain feature (e.g. `product-card.tsx`) stays inside that feature, is not promoted to `shared/` unless reused by a second feature.

New forms should reuse `@/components/shared/form/InputField` (RHF-integrated) rather than binding `ui/input.tsx` directly to `useController` again.

## Response envelope

Backend responses are wrapped: `{ data: T }`. API functions unwrap this before returning to hooks/components (see `products.api.ts`). New API functions must follow the same unwrap-at-the-boundary pattern so components never see the envelope.
